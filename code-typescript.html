TypeScript et SQL — comment tout ça fonctionne

Mis à jour le vendredi 16/10/2026 à 07h35 (heure de Casablanca) · relevé dans le code de la version en ligne ; chaque affirmation se vérifie dans le dépôt de travail

Ava Manager parle deux langues. TypeScript pour ce que l'application fait (écrans et serveur), SQL pour ce qu'elle garde (les données, et les règles qui les protègent). Les deux se surveillent : si l'un se trompe, l'autre refuse.

L'image à retenir : un restaurant

La salle et la cuisine = TypeScript

La salle, ce sont les écrans : ce que voit l'utilisateur. La cuisine, c'est le serveur : il reçoit la commande, vérifie qui la passe et ce qu'il a le droit de demander, puis prépare la réponse.

  • Même langue pour les écrans, le serveur et les tests
  • Les règles du métier y sont écrites, une fois chacune

Le garde-manger sous clé = SQL (PostgreSQL)

C'est la base de données : toutes les fiches, les prestations, les montants. Elle a son propre règlement, et elle l'applique même si la cuisine se trompe.

  • Le cuisinier n'a que les clés dont il a besoin
  • Il ne peut jamais tout vider : le droit d'effacer lui est retiré

Le recruteur clique sur « Archiver ».L'écran envoie la demande au serveur, avec l'identité du compte connecté.

Pourquoi TypeScript

Ce qu'on voulaitCe que TypeScript apporte ici
Un seul langage du haut en basLes écrans, le serveur et les tests parlent la même langue. Un changement qui traverse les trois se fait sans traduire, et une seule personne peut tout relire. C'est le choix écrit dans les décisions techniques de départ.
Des règles écrites une foisLes 94 actions mesurées le 11/10 sont chacune déclarées une seule fois : droits, validation et réglages en découlent. On ne peut pas oublier une règle sur un seul chemin.
Des fautes trouvées avant la mise en ligneTypeScript vérifie que les pièces s'emboîtent avant que le code ne tourne. Exemple réel : le 14/10, il a signalé une erreur dans le calcul des projets, présente dans la version en ligne ; elle est corrigée depuis le Livrable 1.
Une interdiction qui ne dépend pas d'une relectureLe code d'une action ne peut pas lire une valeur brute envoyée de l'extérieur : cette possibilité n'existe plus dans son type. Un humain peut l'oublier, la machine non.

Versions : TypeScript 5.9 en mode strict · Node 22 · Fastify 5 (serveur) · React 19 et Vite 7 (écrans) · shadcn/ui et Tremor (composants).

Pourquoi SQL, et pourquoi la base garde ses propres règles

Ce qu'on voulaitCe que la base apporte ici
Des données qu'on ne perd pasPostgreSQL est une base éprouvée. L'application n'a pas le droit d'effacer : on archive, on ne supprime pas. Les journaux ne se réécrivent pas.
Une deuxième barrièreLes droits sont posés colonne par colonne dans la base. Même un défaut du code ne peut pas écrire là où la base n'a pas ouvert la porte. Exemple réel : des colonnes modifiables sans raison ont été trouvées (défaut P-325) ; le correctif remet le code et la base d'accord (soit une action écrit ces colonnes, soit le droit est retiré).
Des changements qu'on peut défaireChaque changement de la base est un fichier numéroté (166 en ligne le 16/10), qui ne se réécrit jamais. Avant chaque mise en ligne, un point de retour (code, base, fichiers) est fait et vérifié : au moindre échec, on revient en arrière.
Le SQL reste du SQLOn n'écrit pas la base en TypeScript : les droits, les contraintes et les migrations restent dans le langage de la base. Le correcteur protège le code ; le SQL protège les données.

Comment on s'assure que ça tient

QuoiComment
Chaque règle a son contrôleUn test numéroté (P-xxx), 588 dans le code. Un test qui ne devient pas rouge quand on casse la règle est « aveugle » et refusé.
Avant chaque mise en ligneQuatre contrôles : les droits, les fuites entre comptes, l'argent, les changements de la base.
Qui écrit quoiLa session Code écrit le serveur et les écrans ; seule la session Tests écrit les tests et les changements de la base. Celui qui écrit une règle n'est jamais celui qui la vérifie.

ConstatCe que ça veut dire
Écrans et serveur ne partagent pas leurs « formes »Les écrans redéclarent à la main ce que le serveur envoie. Une évolution du serveur peut casser un écran sans alerte automatique.
La vérification TypeScript n'est pas encore automatiqueTests la lance à la main ; elle n'est pas dans la chaîne des contrôles. À brancher.
Il reste des valeurs du métier écrites dans le code15 valeurs doivent venir de la base (tâche n° 49).
Le texte de décision de départ est en retardIl parle de « pages rendues par le serveur » ; les écrans sont devenus une application React.

Les mots, en clair

Serveur
Le programme qui tourne en permanence, reçoit les demandes des écrans et leur répond.
Action (ou commande)
Une chose qu'on peut demander : « créer un candidat », « archiver ». Chacune est déclarée une fois.
Droit
Ce qu'un compte a le droit de voir ou de faire. Il est contrôlé deux fois : par le serveur, puis par la base.
Base de données
Le coffre où sont rangées toutes les informations.
Changement de la base (migration)
Un fichier numéroté qui modifie la structure ou les droits de la base. Il ne se réécrit jamais.
Point de retour
Une sauvegarde complète faite juste avant une mise en ligne, pour revenir en arrière si besoin.
Contrôle (ou porte)
Un test automatique, numéroté P-xxx, qui vérifie une règle.
