## ⭐⭐ PRINCIPE AJOUTÉ LE 17/09 AU SOIR — AHMED

> « Toutes les règles doivent être paramétrables. Rien ne doit être codé en dur, pour qu'on puisse changer les décisions comme on veut : ces décisions vont différer d'une société à une autre. Toute décision qui est une **bifurcation avec plusieurs options** doit être paramétrable. C'est ce qui fait la richesse des bons managers. Très, très important. »

| | Ce que c'est | Où ça vit |
|---|---|---|
| **POLITIQUE** | une bifurcation à options (A/B/C) : F3, F5, F20, F23, F26, F29–F35, G1–G13, DEC-04/06/10, variantes ATL… | table `politique` — valeur par défaut = la décision d'aujourd'hui, changeable en admin, tracée (ADR-004) |
| **MUR** | ce qui garde les données **vraies**, pas une option : candidat jamais sur prestation, XOR du positionnement, ressource immuable sur prestation, snapshot jamais réécrit, jamais de DELETE, un porteur par action | contraintes DB — **pas** paramétrables, sinon rien n'est garanti |
| **RÉFÉRENTIEL** | les listes de valeurs : états, types, étapes | tables de référentiel à **catégorie sémantique**, valeurs système protégées, ajout/renommage en admin (CdC IV.G) |

⛔ Le code ne contient **aucun `if` sur une bifurcation** sans clé au registre des politiques. Un `if` codé en dur sur un choix métier = refus en revue.

⚠️ Le registre dit, ligne par ligne, lequel est politique et lequel est mur. **Une ligne mal classée se conteste avec une source, pas avec un avis.**
